# 呼吸机与端侧 AI 串口协议（2026-08-07）实施说明

本工程以仓库根目录的
`呼吸机与端侧AI串口通讯协议20260807(1).docx` 为实现基线。

## 已采用的协议口径

- UART：230400、8N1、无硬件/软件流控。
- 帧结构：`AA 55 | TYPE | SEQ | DSID_LE | STATE | LEN_LE | CODE | CHECK`。
- `CHECK`：从 `TYPE` 到 `CODE` 逐字节求和，取低 8 位。
- 单帧总长度最多 1024 字节，因此固定开销 10 字节、`CODE` 最多 1014 字节。
- `SEQ` 按发送方向跨 TYPE 全局递增，255 后回到 0。
- `DSID` 只能使用 1～65535；不再使用旧实现中的 `DSID=0` 结束标记。
  文档没有说明 DSID 可回绕，因此同一逻辑对象到 65535 后继续分片会报错，
  不会静默回到 1。
- 上行提问结束由 `STATE=3` 表示；下行整轮音频结束由最后一个带数据的
  `0x11/STATE=1` 表示。
- `0x01/0x02` 的空 `STATE=0(NULL)` 帧作为保活安全忽略；若 NULL 帧携带 CODE
  则视为格式错误。

## TYPE 路由

| 方向 | TYPE | 当前工程行为 |
|---|---:|---|
| MCU→AI | `0xAA` | 校验固定 48 字节握手、两把 KEY、经纬度和 IMEI；以 `0x14` 回复结果 |
| MCU→AI | `0x01` | 按 `STATE=1/2/3` 和连续 DSID 累积 OPUS，仅在 3 时提交 ASR |
| MCU→AI | `0x02` | 按 `STATE=1/2/3` 累积 UTF-8，仅在 3 时提交 LLM |
| MCU→AI | `0x03` | 校验并在内存保存最新设备信息 JSON，不送入 LLM |
| MCU→AI | `0x04` | 校验并在内存保存最新睡眠数据 JSON，不送入 LLM |
| MCU→AI | `0x05` | 读取 1 字节 AI 状态：NULL/休眠/启动/节能 |
| AI→MCU | `0x11` | MP3 16 kbps、单声道，CODE≤1014；整轮末片 `STATE=1` |
| AI→MCU | `0x12` | 固定结构的控制 JSON |
| AI→MCU | `0x13` | `STATE=0` 提问文本，`STATE=1` LLM 回答文本 |
| AI→MCU | `0x14` | 版本、运行状态和异常 JSON；未定义的 STATE 暂固定为 0 |

握手完成前，业务帧会被拒绝。任何 `0xAA` 都会先撤销旧会话；只有
CHECK、DSID、48 字节格式和密钥全部验证通过后，才会建立新会话并重建
上行 SEQ 基线。
CHECK、SEQ、DSID、JSON 或状态异常会记录日志并发送 `0x14`。
所有协议文本在完整拼包后做严格 UTF-8 验证，允许一个 UTF-8 码点跨帧。

联调前置约定：MCU 上电/重连后的首个有效会话帧必须是 `0xAA`，其 DSID 必须为 1；
AI 成功写出 `0x14` 回复后才接受业务帧；握手后第一个业务帧的 SEQ 必须紧接
握手 SEQ（包含 255→0 回绕）。若 MCU 不遵守这一时序，当前安全门禁会拒绝全部业务帧。

## 对原协议歧义的处理

1. 第 4 章总表定义 `0x04=睡眠数据、0x05=AI状态`，第 5 章误写成
   `0x05/0x06`。正式实现采用总表；接收端额外兼容 `0x06` 作为 AI 状态并告警，
   但不会发送 `0x06`。
2. 第 4 章称 `0x13` 为 JSON，第 5 章和示例均为普通文本；实现采用原始 UTF-8。
3. 文档未定义 `0x03/0x04` 多帧结束条件，因此当前要求每条 JSON 在一个
   `DSID=1` 帧内完成。若数据会超过 1014 字节，需要协议方补充总长度或结束状态。
4. 文档只写上行音频“16 kbps、单声道”，未定义 codec、采样率和包边界；当前保留
   既有的 Opus、16 kHz、每包 80 字节假设，必须与 MCU 固件联调确认。
5. `0x12` 没有 MCU→AI 执行 ACK、命令 ID、结果或超时定义。因此工程仍按 §6.5
   在播报结束后 fire-and-forget 下发控制，不能据此声称 MCU 已执行成功。
6. 协议握手同时传输明文、密文且使用固定 KEY，没有 nonce/MAC；当前实现只能用于
   格式兼容和误码校验，不能防窃听或重放。
7. `0x12/0x13/0x14` 没有定义多帧总长或末帧标志。当前发送端仍按通用 DSID
   规则分片；联调时应尽量保证单条 JSON/文本不超过 1014 字节，并向协议增加
   总长或末帧语义。
8. `0x03/0x04` 目前只保存进程内“最新一条”，重启后丢失。若“存储”要求持久化
   或历史记录，需再明确数据库、保留周期和隐私要求。
9. 新 `STATE=1` 会立即作废旧任务代次、停止 UART 旧数据下发，并拒绝迟到的
   TTS 回调。但 ASR/LLM/TTS 底层 HTTP/服务端推理尚不支持强制抢占：旧请求可能
   继续占用资源，但其结果不会混入新会话。尤其是已进入 `/audio` 下载的
   TTS 流仍可占用并发槽，最长受 `TTS_TIMEOUT_SEC=300` 秒限制；尚未发起 HTTP
   的排队任务会立即退出。
10. 协议没有明确 DSID 的重置作用域。当前约定是：`0x01/0x02` 每次新问话从 1
    开始；每条 `0x12/0x13/0x14` 从 1 开始；`0x11` 在同一轮回答的多个语音句段间
    持续连续，新轮回答才重置为 1。这一点必须与 MCU 固件采用相同口径。
11. 附录写“随机数对 3 取模”，但只定义 KEY199/KEY218 两把密钥和 STATE 0/1。
    当前实现明确拒绝 STATE=2；MCU 必须改为只产生 0/1（例如 mod 2），或者由
    协议方正式增加第三把密钥和 STATE=2 的映射。否则字面实现会约有 1/3 概率
    握手失败。
12. `0x02` 实现按 TYPE 表的 1/2/3 状态机执行，必须看到 `STATE=3` 才提交 LLM；
    即使问题很短，MCU 也需在 `STATE=1` 后再发 `STATE=3`（CODE 可为空）。如果 MCU
    将唯一的 `STATE=1` 帧同时视为结束，当前 AI 不会提交该问题。

## 自动化验证

```bash
cmake -S audio_pipeline -B audio_pipeline/build \
  -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build audio_pipeline/build --parallel
ctest --test-dir audio_pipeline/build --output-on-failure
```

`uart_protocol_test` 覆盖帧边界、大小端、CHECK、SEQ 回绕/跳号、两把握手 KEY、
非法握手不重置 SEQ、UTF-8 跨帧/非法编码、文本状态机、噪声/逐字节解析、
`0x13` 状态、`0x11` 分片/末帧状态，以及取消后的旧 TTS 代次不得下发。
